# Research: bridge recording constraints from pi-voice-stt, macOS, and OpenSSH

**Scope.** Planning only. This audit compares `pi-dictation`’s current recording guarantees with the first-party `cgarrot/pi-voice-stt` bridge at pinned revision [`d57f642b0cc4b3bbdd8784d05405455172fa7d41`](https://github.com/cgarrot/pi-voice-stt/tree/d57f642b0cc4b3bbdd8784d05405455172fa7d41), Apple documentation, and OpenSSH manuals. “Documented fact,” “prior-art pattern,” and “recommendation/inference” are deliberately separated below.

## Summary

The bridge should be a separate, opt-in recorder backend whose Mac component—not Pi and not the SSH connection—owns microphone permission, recording state, a hard duration limit, cleanup, and production of bounded PCM16 mono WAV. A stable macOS app identity is the safest permission boundary: Apple documents app-scoped consent and the required usage description/authorization flow. Apple does not document a microphone-specific attribution contract for arbitrary command-line/LaunchAgent process trees, so the chosen identity and launch topology still require real-device validation.

For transport, OpenSSH remote forwarding can expose either a loopback TCP listener or a Unix-domain socket on the VPS and carry it to a Mac TCP/Unix socket over the encrypted channel. Prefer Unix sockets at both ends when deployment compatibility is established, but treat SSH as a byte stream, not a request or transaction protocol: application framing, request/session IDs, size/time bounds, idempotent cleanup, ambiguous-outcome recovery, and independent local expiry are required.

## Repository constraints already established

These are current local facts, not properties of the prior art:

- [`README.md`](../../README.md) states that recorder/transcriber processes are isolated, bounded, and cleaned on cancellation/session shutdown; recorder output is PCM16 mono WAV for truthful live levels; recordings use private `0700` temporary directories; and an independent process-group watchdog stops recording after `maxRecordingMs`, even after abrupt Pi exit.
- [`extensions/pi-dictation.ts`](../../extensions/pi-dictation.ts) currently serializes lifecycle through `idle → starting → recording → stopping`, prevents concurrent recorder starts, bounds recorder stderr, owns a private temporary WAV, uses an independent shell watchdog, stops the whole process group, aborts transcription, and deletes the recording directory. It polls a *growing local WAV* for live levels.
- [`extensions/recorder.ts`](../../extensions/recorder.ts) and [`test/recorder.test.cjs`](../../test/recorder.test.cjs) define and test local macOS capture with FFmpeg AVFoundation `:default`, PCM16 mono at 16 kHz; [`test/live-level.test.cjs`](../../test/live-level.test.cjs) covers incremental WAV reading for truthful levels.

**Constraint R1 (must preserve).** A bridge is another recorder implementation, not a bypass around the state machine. It must preserve: one active recording; bounded start/stop/cancel; cancellation and shutdown cleanup; an independent maximum duration that survives Pi/SSH death; private temporary storage; bounded diagnostics and audio; minimum-valid-output checks; and complete PCM16 mono WAV output.

**Constraint R2 (live-level truthfulness).** A final-body-only bridge cannot feed the existing growing-WAV level reader while recording. The map requires actual live level history while ruling continuous audio streaming out of scope, so the Mac must send authenticated, bounded level observations during capture and deliver the final WAV separately. Never synthesize activity; the downstream ticket must define cadence, scale, ordering, staleness, and failure fallback.

## Documented facts

### macOS microphone authorization and identity

1. Since macOS 10.14, the user must explicitly grant each app microphone access. macOS remembers the response, and the user can later change access in Privacy & Security → Microphone. Apple requires `NSMicrophoneUsageDescription`, describing why the app requests the microphone. [Apple: Requesting authorization to capture and save media](https://developer.apple.com/documentation/avfoundation/requesting-authorization-to-capture-and-save-media) · [Apple: NSMicrophoneUsageDescription](https://developer.apple.com/documentation/bundleresources/information-property-list/nsmicrophoneusagedescription)
2. Apple says to query `AVCaptureDevice.authorizationStatus(for: .audio)` before configuring capture. For `.notDetermined`, call `requestAccess(for: .audio)` at an appropriate user-initiated time; the API exposes authorized, denied, restricted, and not-determined states. [Apple: AVCaptureDevice requestAccess](https://developer.apple.com/documentation/avfoundation/avcapturedevice/requestaccess(for:completionhandler:)) · [Apple: authorization guide](https://developer.apple.com/documentation/avfoundation/requesting-authorization-to-capture-and-save-media)
3. Apple describes `com.apple.security.device.audio-input` as the entitlement allowing built-in-microphone/Core Audio input and says to add it under Hardened Runtime. Thus a hardened-runtime bridge app needs this entitlement; an unsigned/ad-hoc non-hardened tool is not evidence that a hardened distributed app will work without it. [Apple: Audio Input Entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.device.audio-input)
4. Apple Support describes microphone controls and troubleshooting in terms of the *app used to record*, including no sound, no waveform, or motionless meters. The microphone-use indicator reports current/recent microphone use. [Apple: Control access to the microphone](https://support.apple.com/guide/mac-help/control-access-to-the-microphone-on-mac-mchla1b1e1fe/mac) · [Apple: If you can’t record audio](https://support.apple.com/en-us/102071)
5. In Apple staff guidance about Full Disk Access—not microphone authorization—Apple DTS says TCC identifies “responsible code” for command-line tools using an algorithm that is undocumented and has changed. This is cautionary evidence about extrapolating TCC behavior, not a documented microphone-attribution rule. [Apple Developer Forums: How to grant command line tools full disk access](https://developer.apple.com/forums/thread/756510)

**Implication M1.** The supported design should put capture APIs in a stable app bundle with a stable bundle identifier and usage string, and have that app—not `ssh`, Terminal, Pi, Node, or a changing FFmpeg child—be the clear microphone accessor. A CLI/FFmpeg fallback may remain diagnostic or explicitly best-effort. Because Apple does not publish a microphone-specific responsibility contract for arbitrary command-line descendants, attribution to Terminal/cmux must not be treated as a product invariant.

**Implication M2.** Installation should include an interactive permission preflight launched in the user’s GUI session. It should distinguish every AV authorization state and perform a short real capture/level check; user-visible silence/motionless meters mean process exit alone is not a sufficient success test. Do not first trigger consent from an unattended LaunchAgent. Whether a background-only (`LSUIElement`) LaunchAgent reliably presents the first prompt on every supported macOS release remains an open validation question.

### OpenSSH forwarding, security, and failure semantics

1. `RemoteForward` forwards a TCP port **or Unix-domain socket on the remote machine** over the secure channel to a TCP or Unix-socket destination on the local machine. A path containing `/` is interpreted as a Unix socket. With no bind address, TCP remote forwards default to loopback; wildcard/non-loopback binding depends on server `GatewayPorts`. [OpenSSH `ssh_config(5)`: RemoteForward](https://man.openbsd.org/ssh_config.5#RemoteForward)
2. `ssh -N` executes no remote command and is intended for forwarding-only connections. [OpenSSH `ssh(1)`: `-N`](https://man.openbsd.org/ssh.1#N)
3. `ExitOnForwardFailure yes` only proves that requested listeners were initially established. OpenSSH explicitly says it does **not** make SSH exit when later connections to the ultimate forwarding destination fail. [OpenSSH `ssh_config(5)`: ExitOnForwardFailure](https://man.openbsd.org/ssh_config.5#ExitOnForwardFailure)
4. `ServerAliveInterval` sends protocol-level probes after inactivity; `ServerAliveCountMax` disconnects after unanswered probes (default count 3). These detect an unresponsive SSH peer, not application health or completion of a recording operation. [OpenSSH `ssh_config(5)`: ServerAliveInterval](https://man.openbsd.org/ssh_config.5#ServerAliveInterval) · [ServerAliveCountMax](https://man.openbsd.org/ssh_config.5#ServerAliveCountMax)
5. For forwarded Unix sockets, `StreamLocalBindMask` defaults to `0177`, intended to create an owner-only socket, though OpenSSH warns that not all operating systems honor Unix-socket modes. `StreamLocalBindUnlink` defaults to `no`; an existing socket path prevents setup unless unlinking is enabled. Both client and server have settings with these names. For a `RemoteForward` Unix listener on the VPS, `sshd` creates that listener and its `sshd_config` controls mask/unlink behavior; the Mac companion creates and owns its destination socket separately. [OpenSSH `ssh_config(5)`](https://man.openbsd.org/ssh_config.5#StreamLocalBindMask) · [`sshd_config(5)`: StreamLocalBindMask](https://man.openbsd.org/sshd_config.5#StreamLocalBindMask) · [StreamLocalBindUnlink](https://man.openbsd.org/sshd_config.5#StreamLocalBindUnlink)
6. Server policy can disable all forwarding, independently allow/deny StreamLocal forwarding, restrict remote TCP listen addresses/ports with `PermitListen`, and control exposure with `GatewayPorts`. By default remote TCP forwards bind loopback; `GatewayPorts` can broaden that. [OpenSSH `sshd_config(5)`: AllowStreamLocalForwarding](https://man.openbsd.org/sshd_config.5#AllowStreamLocalForwarding) · [PermitListen](https://man.openbsd.org/sshd_config.5#PermitListen) · [GatewayPorts](https://man.openbsd.org/sshd_config.5#GatewayPorts)
7. A dedicated authorized key can start restricted and selectively re-enable port forwarding; `permitlisten` limits the remote listener a key may request. [OpenSSH `sshd(8)`: AUTHORIZED_KEYS FILE FORMAT](https://man.openbsd.org/sshd.8#AUTHORIZED_KEYS_FILE_FORMAT)

**Implication S1.** A successful tunnel start, a healthy SSH process, and a healthy recorder are three different states. Doctor/status must check all three. Each application operation needs its own timeout and protocol response.

**Implication S2.** If Unix sockets are chosen, use a private parent directory, an owner-only bind mask, explicit stale-socket policy, and a per-user/per-install path. Do not assume filesystem mode enforcement on every OS; application authentication or peer-credential validation remains defense in depth. Verify the deployed VPS OpenSSH permits remote StreamLocal forwarding.

## Prior-art patterns from pi-voice-stt

The bridge first appeared in commit [`a07a10931900b762edaa92eab584ec2599a15e89`](https://github.com/cgarrot/pi-voice-stt/commit/a07a10931900b762edaa92eab584ec2599a15e89) and is audited here at the pinned current revision.

### Patterns worth retaining

1. **Opt-in backend isolation.** `capture.type: "bridge"` selects a bridge recorder while local FFmpeg remains the default; downstream controller/provider behavior is unchanged. [Bridge guide](https://github.com/cgarrot/pi-voice-stt/blob/d57f642b0cc4b3bbdd8784d05405455172fa7d41/docs/macos-bridge.md) · [example config](https://github.com/cgarrot/pi-voice-stt/blob/d57f642b0cc4b3bbdd8784d05405455172fa7d41/examples/bridge-groq.json)
2. **Small lifecycle protocol.** The Mac daemon exposes health/start/stop/cancel; start rejects a second active capture (409), stop returns WAV, cancel discards, and health reports active/config state. This maps cleanly to a recorder handle. [Native daemon](https://github.com/cgarrot/pi-voice-stt/blob/d57f642b0cc4b3bbdd8784d05405455172fa7d41/tools/macos-bridge-native.swift) · [Node fallback](https://github.com/cgarrot/pi-voice-stt/blob/d57f642b0cc4b3bbdd8784d05405455172fa7d41/tools/macos-bridge-server.mjs)
3. **Mac-owned safety.** Both daemons apply `maxSeconds`, hold only one active recording, create temporary WAVs, delete them on stop/cancel, and reject too-small audio; the native daemon and VPS client additionally inspect PCM amplitude for silent capture. [Native daemon](https://github.com/cgarrot/pi-voice-stt/blob/d57f642b0cc4b3bbdd8784d05405455172fa7d41/tools/macos-bridge-native.swift) · [bridge recorder](https://github.com/cgarrot/pi-voice-stt/blob/d57f642b0cc4b3bbdd8784d05405455172fa7d41/src/audio/bridge-recorder.ts)
4. **Least exposure and layered auth.** The daemon and remote TCP forward use explicit `127.0.0.1`; a random 32-byte token is stored mode `0600` and required by normal installation; non-loopback plain HTTP is rejected by client configuration. [Installer](https://github.com/cgarrot/pi-voice-stt/blob/d57f642b0cc4b3bbdd8784d05405455172fa7d41/tools/install-macos-bridge.sh) · [bridge guide security model](https://github.com/cgarrot/pi-voice-stt/blob/d57f642b0cc4b3bbdd8784d05405455172fa7d41/docs/macos-bridge.md#security-model)
5. **Persistent user services and diagnosability.** Separate LaunchAgents supervise daemon and `ssh -NT`; SSH uses `ExitOnForwardFailure`, server-alive settings, and dedicated logs; `/health` supports doctor output. [Installer](https://github.com/cgarrot/pi-voice-stt/blob/d57f642b0cc4b3bbdd8784d05405455172fa7d41/tools/install-macos-bridge.sh)
6. **Native permission identity.** When Swift is available, the installer builds an app bundle with a stable bundle ID, `NSMicrophoneUsageDescription`, AVFoundation capture, and `LSUIElement`; the native process explicitly checks/requests audio authorization. [Installer](https://github.com/cgarrot/pi-voice-stt/blob/d57f642b0cc4b3bbdd8784d05405455172fa7d41/tools/install-macos-bridge.sh) · [native daemon](https://github.com/cgarrot/pi-voice-stt/blob/d57f642b0cc4b3bbdd8784d05405455172fa7d41/tools/macos-bridge-native.swift)

These are prior-art patterns, not verified guarantees for `pi-dictation`. The pinned tree contains configuration/controller tests but no dedicated bridge transport test file, so source behavior should not be treated as a fully tested contract.

### Failure modes not to copy unchanged

| Severity | Location | Failure mode | Design constraint |
|---|---|---|---|
| **Blocker** | `src/audio/bridge-recorder.ts`, both daemons | Requests have no recording/session ID. If `/start` times out after the Mac started, the VPS believes start failed while a global recording remains active. If `/stop` response is lost, retry sees “no active recording” and audio is lost. Any authenticated client can stop/cancel the one global session. | Give every recording a cryptographically random operation/session ID. Make start idempotent for that ID; bind stop/cancel to it; retain terminal result briefly for safe retry; define conflict/reconciliation behavior. |
| **High** | `tools/macos-bridge-native.swift`, `tools/install-macos-bridge.sh` | Permission reliability is asserted from a locally built, ad-hoc-signed background app. The installer does not include the hardened-runtime audio-input entitlement and does not provide an explicit interactive permission preflight. | Ship/test one stable signed identity; include entitlement when hardened; add setup-time authorization and real-audio preflight; validate upgrades, moved app, denial/regrant, and OS upgrades. |
| **High** | `tools/install-macos-bridge.sh` tunnel cleanup | To clear a stale TCP forward, the script remotely parses `ss` output and may `sudo kill` an `sshd-session` PID. Matching by port/process text is race-prone and requires broad remote privilege. | Never kill server sshd processes by scraped PID. Prefer unique Unix-socket paths plus controlled unlink, or normal connection ownership/control commands and supervised reconnection. |
| **High** | `src/audio/bridge-recorder.ts`, native daemon | The VPS buffers the entire response with `arrayBuffer()` before writing; the native daemon loads the entire WAV into `Data`. There is no declared maximum response/body length enforced by the client. | Stream to a private file with a strict byte cap derived from sample rate/channels/duration; validate Content-Length when present but do not trust it; abort and delete on overflow/truncation. |
| **High** | bridge protocol generally | SSH is a stream; disconnect can occur between side effect and acknowledgment. There is no transaction boundary or exactly-once guarantee supplied by forwarding. | Protocol must define framing, IDs, idempotency, reconnect/status lookup, EOF/truncation handling, and checksum/declared length for final audio. |
| **Medium** | `tools/macos-bridge-server.mjs` | The max-duration timer terminates FFmpeg but leaves `active` set until a later stop/cancel; a subsequent start conflicts. SIGTERM/SIGKILL supervision covers only the direct FFmpeg process, not an arbitrary descendant group. | Local expiry must atomically transition state, finalize/discard per policy, clean temp data, and allow the next start. Use the repository’s process-owner/process-group safety model where subprocesses exist. |
| **Medium** | both daemons | Empty token means “allow all.” Both prior-art daemons use loopback TCP, so any local process or user able to connect may call the API; even an owner-only Unix socket would not authenticate another process of that owner. Token comparison is simple equality. | Production installation must fail closed if credential/peer validation is unavailable. Keep token files private; redact them from config/status/logs; consider rotation and constant-time comparison. |
| **Medium** | `/health` and `/stop` | Health leaks device/config details to any authorized local caller; stop errors may include retained FFmpeg stderr. Error text crosses from Mac to VPS/UI. | Minimize health fields; cap and sanitize all remote error bodies before logging/display; never return command lines, environment, token, or sensitive paths. |
| **Medium** | final-response API | Stop transfers only after capture ends, increasing perceived latency and preventing existing growing-WAV polling. Long WAV responses are vulnerable to midstream truncation. | Preserve live history through a separate authenticated bounded level signal, then transfer the final WAV with length/hash validation, byte caps, and truncation handling. |
| **Low** | `tools/install-macos-bridge.sh` | Fixed port and copied SSH host settings can collide or drift; installer copying only a few host fields can omit proxy/jump/security policy from the original alias. | Prefer a dedicated `Host` stanza that inherits/includes deliberate settings, or invoke the user’s existing alias with explicit `-R`; choose collision-resistant per-install socket names. |

## Recommended bridge contract

The following are recommendations/inferences, not claims made by Apple or OpenSSH.

### Architecture

1. **Recorder abstraction:** add an explicit recorder interface behind existing lifecycle code. Local command and bridge implementations return the same logical handle (`stop`, `cancel/dispose`, output path/level capability). Bridge configuration is opt-in and validated before external work.
2. **Mac capture owner:** a user-session macOS app bundle owns AVFoundation access and the active recording. A LaunchAgent may keep it available, but installation/preflight opens the stable app interactively once. The app opens the mic only during an authenticated start-to-stop window.
3. **Transport:** preferred topology is a dedicated `ssh -NT` connection from Mac to VPS with a **remote Unix-socket listener forwarding to a Mac Unix socket**. This avoids port collisions and accidental network exposure. Fall back to explicit `127.0.0.1` TCP on both ends only where StreamLocal forwarding is unavailable. Never use wildcard binds.
4. **Protocol:** HTTP over Unix sockets is acceptable if implemented with strict headers/content lengths, but a small length-prefixed protocol is also viable. In either case, the wire is a byte stream: cap header/frame lengths; reject malformed, duplicate, out-of-order, oversized, and trailing data; include protocol version, request ID, recording ID, operation, status, content length, and final audio digest. Level observations need explicit sequence/timestamp and scale semantics without carrying continuous audio.
5. **State/recovery:** start creates or resumes a named recording ID. Status reports that ID and state. Stop is idempotent and retains a completed result for a short bounded retry window; cancel is idempotent and wins over further stop delivery. On reconnect the VPS reconciles status rather than guessing. Unknown IDs fail without touching another recording.
6. **Independent bounds:** Mac enforces maximum wall-clock duration and maximum bytes even with no tunnel. VPS independently bounds every request and received byte count. A tunnel/extension crash must leave at most one locally bounded recording that is automatically stopped and deleted/finalized according to a documented policy.
7. **Audio validity:** require a complete RIFF/WAVE containing expected PCM16LE, mono, nominal 16 kHz (or explicitly negotiated values); validate chunk bounds, duration/size consistency, and nontrivial signal without assuming “small” is always silent. Transfer to a private temporary file and atomically hand it to transcription only after full validation.
8. **Security:** install socket/token/config directories mode `0700` and secrets `0600`; fail closed when auth is missing; use per-install random credentials; restrict the SSH key/account to the exact forwarding need where operationally possible; set `GatewayPorts no`; avoid agent forwarding, PTY, remote shell, and unrelated forwards for a dedicated tunnel credential. Host-key verification must remain enabled.
9. **Observability:** distinguish `permission-denied`, `permission-restricted`, `device-unavailable`, `already-recording`, `tunnel-setup-failed`, `destination-unreachable`, `request-timeout-ambiguous`, `audio-truncated`, `audio-too-small/silent`, and local-limit expiry. Doctor should report permission identity/status, daemon protocol compatibility, destination health, SSH listener health, and safe audio preflight without exposing secret/path details.

### Required tests for the implementation handoff

- Lifecycle parity: toggle races, cancel while starting/recording/stopping, session shutdown, Pi `SIGKILL`, tunnel death, Mac daemon death/restart, Mac sleep/wake, network partition, and maximum duration after all remote clients disappear.
- Ambiguous outcomes: drop connection immediately before/after start/stop side effects and acknowledgments; retry same ID; stale/foreign ID cannot stop active recording.
- Stream safety: split every frame boundary, slow reader/writer backpressure, early EOF, extra bytes, false/huge length, malformed WAV/chunks, oversized diagnostics, and maximum-length audio.
- macOS identity matrix on supported releases: fresh install, first prompt, deny, regrant in Settings, restricted state if reproducible, app update/re-sign, moved app, reboot, login LaunchAgent, built-in/USB mic, disconnected/default-device change, all-zero samples.
- SSH matrix: TCP and StreamLocal capability detection; forwarding prohibited by server; VPS `sshd` mask/unlink settings; stale socket with unlink off/on; wrong socket owner/mode; remote listener collision; destination absent after successful forward; host-key failure; key/passphrase unavailable under LaunchAgent; server alive timeout and reconnect.
- Existing contract: output is a valid final PCM16 mono WAV; authenticated level observations preserve truthful live history without continuous audio streaming; temp paths remain private and are removed; no raw audio/token/custom command leaks to doctor, UI, or logs.

## Open questions for downstream tickets

1. **Transport support floor:** Are all target VPS hosts on OpenSSH versions/configurations that support remote StreamLocal forwarding? If not, is loopback TCP an automatic fallback or separately configured?
2. **Identity/distribution:** Will the Mac bridge be source-built/ad-hoc signed, Developer ID signed/notarized, or embedded in another stable app? Which macOS versions are supported, and is Hardened Runtime required?
3. **First-run UX:** How will an interactive user launch permission preflight if Pi itself is remote? How is denial/restriction explained without asking users to grant Terminal/ssh broad access?
4. **Live-level semantics:** The map requires actual level history without continuous audio streaming. What cadence, fixed scale, sequence/timestamp model, staleness rule, and disconnect fallback preserve truthfulness while the final WAV is delivered separately?
5. **Orphan result policy:** At local expiry or tunnel loss, should the Mac retain an encrypted/private completed WAV for a short retry TTL or always delete it? Retention improves recovery but expands privacy exposure.
6. **Multi-client lease attribution:** The map already requires one Mac companion to accept multiple Pi clients while granting one active recording lease. Define authorization namespaces, lease ownership, reject/queue policy, and per-client quotas; a single unattributed global active slot is insufficient.
7. **Tunnel credential:** Can documentation require a dedicated restricted SSH key/account? Exact `authorized_keys` restrictions need integration testing because `restrict`, forwarding re-enable, and TCP-vs-StreamLocal controls differ.
8. **Device selection:** Is system default sufficient, or must the bridge persist AVFoundation `uniqueID` and handle device disappearance/default changes? This intersects the existing microphone-discovery roadmap.
9. **Upgrade compatibility:** What protocol-version negotiation and minimum daemon/client versions are required? Backward compatibility is not a repository constraint, but incompatible peers need a precise doctor error.
10. **Threat model:** Is same-user local malware in scope? That decision determines whether owner-only Unix sockets are sufficient or bearer auth/peer credentials and key rotation are mandatory.

## Gaps and residual risks

- Apple does not publicly specify a stable TCC responsibility algorithm for arbitrary command-line/LaunchAgent process trees. Only real-device validation of the chosen signed app and launch path can close this gap.
- The research did not execute the prior-art bridge or inspect private issue/PR discussion; source and public commit history were audited. Its current pinned tree does not expose dedicated bridge transport tests.
- OpenSSH documents forwarding setup and policy but does not supply application transaction semantics. Exact disconnect/retry guarantees must be designed and tested by `pi-dictation`.
- Relative repository links refer to this checkout. External citations are absolute; `pi-voice-stt` citations are commit-pinned, while Apple and OpenSSH documentation links are live.
